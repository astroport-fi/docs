# Router

## Overview

The Router contract performs multi-hop swaps across Astroport pools, for native and CW20 tokens. Two router versions are live on each chain:

- **Router 2.0** (`astroport-router` 2.0.0) is the recommended router. A hop is either a pool the factory knows for an asset pair (`astro_swap`) or a pool given by address (`pool_swap`). With `pool_swap`, pools that aren't registered in the factory, such as the USDC transmuter on Terra, can be part of a route. `minimum_receive` is required and is the route's only price check.
- **Router 1.3** (`astroport-router` 1.3.1) is still live with its old API: every hop is resolved through the factory, `minimum_receive` is optional and `max_spread` is checked per hop. See [Router 1.3](#router-13).

Router 2.0 is deployed as its own instance. Router 1.x instances keep their old API and can't be migrated to 2.0. The Maker 2.0 contracts swap through Router 2.0.

## Price protection

Pools' own spread checks are disabled on every hop, including single-hop swaps. The only price guarantee is `minimum_receive`: after the last hop, the router checks that the receiver got at least that amount of the ask asset and reverts the whole transaction otherwise. It is required and must be greater than zero.

The bound is only as good as the number you send. Set `minimum_receive` from a price you trust (for example your own quote minus slippage), not from a hop's own simulation. `minimum_receive: "1"` is accepted but protects almost nothing.

Nested routes are refused: a route can't be started while another one is in progress (`RouteInProgress`).

## Choosing pools

`pool_swap` accepts any address. The router checks that the pool's `pair {}` query reports that address and both assets, which catches mistyped routes, but it can't prove a contract is a genuine Astroport pool. Only build `pool_swap` routes from pools you trust.

Each hop offers the router's whole balance of the offer asset. The router holds nothing between transactions, so this is only the route's own funds plus anything sent to the router by mistake.

A route has at most 50 hops. Each hop must offer the asset the previous hop asked for, and a hop can't offer and ask for the same asset.

## ExecuteMsg

### `execute_swap_operations`

Swaps the attached amount along the route. Hops execute one by one and the last one sends the ask asset to `to` (the sender if omitted). Anyone can call it.

The response data contains the total `return_amount` (a `SwapResponseData`). It is only set when the route starts with a native asset; a CW20 `send` resets the response data.

This example, on Terra, swaps 10 LUNA for USDC (Noble) through the factory's LUNA/USDC pool, then USDC for USDC.inj through the USDC transmuter, a pool that isn't registered in the factory. Attach the `uluna` to the message.

| **Variants**      | **Description** |
| ----------- | ----------- |
| [`astro_swap`](focus://json#2:15)    | Swap in the factory's pool for this asset pair. The factory must know a pool for the two assets       |

### `receive`

CW20 receive hook, used when the first offer asset is a CW20 token. Send the token to the router with a CW20 `send` whose `msg` is the base64-encoded `execute_swap_operations` message below (the same fields as the execute message).

<CH.Section>
    <CH.Code>

        ```json json
        {
            "send": {
                "contract": "terra1txm8xcy8mete9e5zh5ktqr4jm4cq4ja8djttg3zkqll64x4ksq7qknaesf",
                "amount": "1000000",
                "msg": "<base64 of the hook message>"
            }
        }
        ```

        ```rust msg.rs
        #[cw_serde]
        pub enum Cw20HookMsg {
            ExecuteSwapOperations {

                minimum_receive: Uint128,

            },
        }
        ```

    </CH.Code>

| ----------- | ----------- | ----------- |
| [`contract`](focus://json#3)   | `String`        | The router address      |

### `execute_swap_operation`

Executes a single hop. Only the router itself can call it; `execute_swap_operations` uses it for every hop.

## Router 1.3

Router 1.3.1 stays live on both chains for existing integrations. Its messages are the 1.x types in [`astroport::router`](https://github.com/astroport-fi/astroport-core/blob/main/packages/astroport/src/router.rs):

- Hops are `astro_swap` only (factory pools). `native_swap` is part of the type but isn't supported on Terra or Neutron, and there is no `pool_swap`.
- `execute_swap_operations` takes `operations`, an optional `minimum_receive`, an optional `to` and an optional `max_spread`. `max_spread` is checked on every hop.
- The `config`, `simulate_swap_operations` and `reverse_simulate_swap_operations` queries have the same shape as in 2.0.

```json
{
    "execute_swap_operations": {
        "operations": [
            {
                "astro_swap": {
                    "offer_asset_info": {
                        "native_token": {
                            "denom": "untrn"
                        }
                    },
                    "ask_asset_info": {
                        "native_token": {
                            "denom": "factory/neutron1ffus553eet978k024lmssw0czsxwr97mggyv85lpcsdkft8v9ufsz3sa07/astro"
                        }
                    }
                }
            }
        ],
        "minimum_receive": "1000000",
        "max_spread": "0.01"
    }
}
```

<Admonition type="info" title="NOTE">
  New integrations should use Router 2.0. It can route through pools the factory doesn't know, and its required `minimum_receive` makes the route's price check explicit.
</Admonition>
